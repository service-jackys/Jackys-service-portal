# Target Architecture Baseline

**Baseline date:** 2026-09-24  
**Status:** Phase 3 implementation baseline; not a production deployment

## Goals and constraints

The replacement must provide a normal web application while the current Google Apps Script and Google Sheets system remains operational. The migration is capability-led: no public redirect, Apps Script change, data import, or production cutover is allowed until the replacement passes the relevant workflow and reconciliation gates.

The private application repository must contain source and safe documentation only. It must not contain customer exports, spreadsheets, credentials, deployment tokens, Supabase service-role keys, Apps Script configuration, or the unrelated Omniroute `config.json`.

## Runtime shape

```text
Customer browser / staff browser
        |
        v
Web service (server-hosted HTML/CSS/JS + Alpine.js)
        |
        v
Express TypeScript API
  |       |        |        |
  v       v        v        v
Auth   PostgreSQL  Storage  Email/ICS adapters
(Supabase)         (private) (disabled by default)
```

The initial implementation remains deliberately small:

- `apps/api`: Express API, route composition, middleware, application services, repositories, and migration-facing endpoints.
- `apps/web`: server-hosted customer and internal UI, progressively enhanced with Alpine.js and normal `fetch` clients.
- `packages/contracts`: Zod schemas, DTOs, enums, API response types, and shared validation rules.
- `packages/db`: migrations, database client, repositories, constraints, and seed helpers.
- `packages/auth`: Supabase session verification and application RBAC helpers.
- `packages/ui`: only shared presentation pieces that prove useful; do not create an abstraction before reuse exists.
- `scripts/import-sheets`: dry-run/apply import tooling with row-level errors and idempotency.
- `scripts/verify-parity`: count, identifier, status, date, amount, and selected-record reconciliation checks.
- `tests/integration`: PostgreSQL-backed tests.
- `tests/e2e`: browser tests for public and staff workflows.

## Data and persistence decisions

Supabase PostgreSQL is the first production target because it provides managed PostgreSQL, Auth, Storage, and operational tooling. Database access must remain behind repositories and use standard PostgreSQL semantics so another hosted provider can be adopted later.

Core Phase 1 tables should include:

- profiles/user linkage, roles, permissions, and role-permission assignments;
- audit/activity events;
- customers and B2B branches/sites;
- technicians and availability;
- complaints and complaint status history;
- appointments and appointment status history;
- legacy-reference mappings and import batches.

Later migrations add job cards, attachments, quotations, inspections, AMC records, VAS sales, proposals, pricing configurations, workbook metadata, reports, and dashboard summaries.

Required database properties:

- primary keys are generated by the database;
- legacy references such as `CMP-yymmdd-XXX`, `APT-YYYY-#####`, `QO-###`, and `JC-###` are preserved in unique columns;
- complaint-to-appointment linkage is represented by a foreign key and an explicit uniqueness rule where business rules require one active appointment per complaint;
- technician rows are locked in scheduling transactions before availability and exact-slot conflict checks, preventing concurrent same-technician bookings;
- draft schedule promotion locks the draft and all referenced complaint/technician rows in deterministic order, then commits appointments, counters, histories, links, complaints, and audits atomically;
- appointment records have no duration column, so ICS output uses a deterministic one-hour event duration;
- number generation is transactional and concurrency-safe;
- status transitions are validated in the service layer and recorded in history/audit tables;
- all multi-record operations use transactions;
- timestamps are stored consistently and rendered in the configured UAE business timezone;
- imports carry source name, source row, legacy identifier, batch ID, and reconciliation status.

## Authentication and authorization

Supabase Auth owns password storage, login, refresh/session lifecycle, and reset flows. The API validates the Supabase access token server-side, resolves the application profile and role assignments from PostgreSQL, and enforces permissions in middleware/service checks.

The legacy roles (`user`, `sales`, `management`, `admin`) and permission keys are migration inputs, not browser-controlled claims. The application may introduce more precise operational roles such as CCE, scheduler, supervisor, technician, and management only after the business permission matrix is approved. A role supplied in request JSON or client storage is never trusted.

Protected operations must include authorization checks even when reached through a UI hidden by role. Sensitive changes require an audit event containing actor, action, target, timestamp, and safe change metadata without storing secrets.

## Storage and file handling

Supabase Storage uses private buckets for job-card attachments and uploaded workbooks. The API validates file size, MIME type, extension, and association before upload. Downloads use short-lived signed URLs after authorization. Files are never made public by default, and the legacy Drive `ANYONE_WITH_LINK` behavior is not carried forward.

Workbook uploads require:

1. authenticated administrator authorization;
2. replacement/version metadata and checksum;
3. private storage;
4. parse/validation preview;
5. explicit apply action;
6. audit event and rollback/version reference.

## API boundaries

The API is organized by capability, not by direct translation of Apps Script function names:

- `/health` for operational checks;
- `/auth` for session-facing operations that remain compatible with Supabase Auth;
- `/public/complaints` for rate-limited complaint submission;
- `/complaints` for protected inbox, detail, notes, and status operations;
- `/appointments` for creation, update, assignment, status, draft promotion, and ICS data;
- `/technicians` and `/customers` for protected masters;
- later `/job-cards`, `/commercial`, `/pricing`, `/files`, `/reports`, `/dashboard`, and `/admin` modules.

Every boundary uses shared Zod validation, consistent error responses, request correlation IDs, structured logging, and explicit permission requirements. Public complaint submission must not expose internal user data or accept internal-only fields such as status, warranty classification, appointment assignment, or final status.

## Frontend strategy

The web service uses server-hosted HTML/CSS/JavaScript with Tailwind CSS and Alpine.js for local state. Alpine is appropriate for forms, tabs, filters, dialogs, and small dashboard interactions; normal `fetch` clients call the API. React is not part of the baseline and should only be reconsidered if the migrated workflows become unmaintainable with the chosen approach.

The first browser journeys are:

1. public complaint registration and confirmation reference;
2. staff sign-in and role-gated navigation;
3. complaint review/update;
4. load complaint into New Request;
5. appointment creation with technician assignment;
6. appointment status/list/calendar views;
7. unauthorized access rejection.

## External adapters and feature flags

Email, WhatsApp helpers, ICS generation, and scheduled/background work are adapter boundaries. Email remains disabled by default until a business sender identity, approved templates, and staging verification exist. ICS generation may be enabled earlier because it is a deterministic download, but it must use the configured public API URL and timezone. The current implementation renders a one-hour event with RFC5545 escaping, CRLF output, persisted `DTSTAMP`, and `Asia/Dubai` as the default timezone.

Render is the initial deployment target connected to a private GitHub repository. Supabase hosts the database/Auth/Storage services. Production configuration is supplied through deployment secrets, not committed files. The existing GitHub Pages landing/redirect repository remains unchanged until production acceptance.

## Security baseline

- Private repository and protected main branch.
- Secret scanning and dependency auditing in CI.
- `.env` ignored; `.env.example` contains names only and no real credentials.
- Helmet/secure headers and bounded JSON/request bodies.
- Rate limiting on public complaint submission and abuse-aware logging.
- CSRF protection strategy documented before cookie-based sessions are introduced.
- Server-side RBAC on every protected route.
- Least-privilege database and storage credentials.
- Private files and signed URLs.
- Parameterized database queries through repositories.
- Audit events for role, pricing, status, import, attachment, and administrative changes.
- No in-memory locks for numbering, linkage, imports, or transitions.
- No customer data, exported sheets, deployment URLs, file IDs, or secrets in source control.

## Verification gates

### Phase 0 gate

- Clean source repository with generated artifacts and secrets excluded.
- Source inventory reviewed against live Apps Script files.
- Architecture and migration safety decisions documented.
- Authorized backup/export procedure defined and tested outside Git.
- No live Apps Script deployment change.

### Phase 1 gate

- API/web shells build and typecheck.
- Local PostgreSQL starts from Docker Compose.
- Migrations apply cleanly and can be rerun safely.
- Auth/session and role checks reject unauthenticated and unauthorized requests.
- Health checks and structured error handling work.

### Phase 2 gate

- A test complaint creates exactly one `CMP-yymmdd-XXX` reference.
- CCE review and status changes are authorized and audited.
- A complaint creates exactly one linked appointment transactionally.
- Failed linkage leaves no partial appointment.
- Technician assignment, drafts, status changes, and ICS pass integration tests.
- Emails remain disabled in migration/staging.

### Cutover gate

- Critical workflow acceptance signed by business users.
- Idempotent imports and reconciliation report signed.
- Attachments and private files verified.
- Production smoke tests pass on HTTPS with configured secrets.
- Public complaint and portal redirects updated only after smoke tests.
- Apps Script remains available as a read-only rollback option for the agreed period.

## Open decisions

1. Final Supabase project and Render service are not created in this Phase 0 workspace.
2. The exact live spreadsheet/Drive export process requires authorized access and must be run outside source control.
3. The final role/permission matrix needs business approval; the current Apps Script permission keys are the starting point.
4. The production email provider, sender identity, and WhatsApp integration contract are not selected.
5. The current deployed Apps Script timezone must be confirmed; the target default is `Asia/Dubai`.
6. The business must define the rollback period and read-only migration window before cutover.
