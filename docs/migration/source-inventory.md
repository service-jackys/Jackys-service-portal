## Server-side source inventory

### Web entry points and integrations

`doGet(e)` serves the internal portal, the public complaint page when `page=complaints`, and technician calendar output when `ics=1`. `getWebAppUrl()` returns the deployed Apps Script URL for links generated by the application.

ICS generation is implemented by `serveTechnicianIcs_`, `buildIcs_`, `icsEscape_`, and `icsStamp_`. The current behavior emits one-hour events for a technician/date and uses the Apps Script timezone. The replacement must use an explicit configured timezone and preserve appointment identifiers in stable event UIDs.

The current scheduler email path is disabled by `SCHEDULER_EMAILS_ENABLED = false`; the send blocks are also commented out. Email must remain disabled by default in migration and staging environments.

### Commercial record sheets and numbering

The generic record layer uses `SHEETS`, `PREFIXES`, and `HEADERS_BY_TYPE`.

`getNextNumber`, `listRecords`, `listRecordsWithIndex`, `saveRecord`, `updateRecordByRowIndex`, `listThomsonProposals`, and `updateThomsonProposal` expose create/read/update behavior. Numbers are currently calculated by scanning the sheet and incrementing the largest suffix. Writes use `LockService`; the replacement must use database sequences or transactional counters and unique constraints rather than an in-memory lock or sheet scan.

The `DataJSON` field preserves the browser payload and is used for reloads. During migration it should be retained in a controlled legacy-payload column or mapping table, not copied into arbitrary JSON without an ownership and retention decision.

Service job card final statuses are `WIP`, `BER`, `Rejected`, `Repair Completed`, and `Spare pending`. `BER`, `Rejected`, and `Repair Completed` are treated as final; non-admin users cannot edit a closed card. Attachments are limited to five per card and 10 MB per file in the current implementation.

### Complaints and appointments

The complaint sheet is `Customer_Complaints` with these columns:

`Timestamp`, `Complaint No`, `Customer Type`, `Customer Name`, `Contact No`, `Customer Email`, `Location / Address`, `Region`, `Brand`, `Model`, `Serial / Item Code`, `Complaint Description`, `B2B Branch / School`, `School Contact Person`, `School Contact Number`, `Customer Number`, `Sales Order No`, `Status`, `CCE Notes`, `Warranty Classification`, `Appointment Date`, `Appointment Time`, `Assigned Technician`, `Final Status`, `Appointment No`, `Updated At`, `Updated By`.

`submitCustomerComplaint` accepts a server-side whitelist of public fields, enforces maximum lengths, validates the email format, requires customer name/contact/description, and creates a `CMP-yymmdd-XXX` reference based on the Apps Script timezone. `listCustomerComplaints` and `updateCustomerComplaint` are scheduler-protected. Complaint statuses are `New`, `Under Review`, `Pending Information`, `Ready for Scheduling`, `Scheduled`, `Closed`, and `Cancelled`.

The schedule sheet is `Schedules` with these columns:

`Timestamp`, `Appointment No`, `Customer Type`, `Customer Name`, `Contact No`, `Customer Email`, `Location / Address`, `Region`, `Brand`, `Model`, `Fault Description`, `Job Warranty`, `Appointment Date`, `Appointment Time`, `Assigned Technician`, `Sales Order No`, `Status`, `Item Code`, `Sub Group`, `School Contact Person`, `School Contact Number`, `Customer Number`, `B2B Branch / School`, `Closed Timestamp`, `Complaint No`.

Appointments use `APT-YYYY-#####` references. `saveSchedule` creates the appointment and updates the linked complaint to `Scheduled` in one locked operation; if the complaint update fails, the new schedule row is deleted. The replacement must implement this as one PostgreSQL transaction with foreign keys and a unique complaint-to-appointment rule. Schedule statuses are `Scheduled`, `In Progress`, `Completed`, and `Cancelled`; closure timestamps freeze completed/cancelled lifecycle timing and are cleared if the appointment is reopened.

`updateSchedule`, `listSchedules`, `updateScheduleTechnician`, and `updateScheduleStatus` support editing, assignment-board reassignment, listing, and status transitions.

### Technicians, B2B customers, and draft schedules

- `Technicians`: `Name`, `Region`, `Phone`, `Email`, `Working Hours Start`, `Working Hours End`, `Active`.
- `B2BCustomers`: `Branch / School Name`, `Contact Person`, `Contact Number`, `Customer Number`.
- `AwaitingSchedules`: `Timestamp`, `BatchId`, `Customer Type`, `Customer Name`, `Contact No`, `B2B Branch / School`, `Location / Address`, `Region`, `Brand`, `Model`, `Item Code`, `Appointment Date`, `Appointment Time`, `DataJSON`.

`saveTechnician`, `listTechnicians`, and `deactivateTechnician` manage soft-deactivated technicians. `createDraftSchedules` creates up to 50 placeholders sharing a batch ID; `listDraftSchedules`, `deleteDraftSchedule`, and `promoteDraftSchedule` manage conversion to real appointments. Draft promotion must be idempotent and transactional in the replacement.

### Authentication, authorization, and audit

The current sheets are:

- `Users`: `Email`, `Name`, `Role`, password hash/salt, first-login flag, session token hash/expiry, created/last-login timestamps.
- `RoleAccess`: role, permissions JSON, updated timestamp, updated by.
- `ActivityLog`: timestamp, email, action, details.

Current roles are `user`, `sales`, `management`, and `admin`. Permission keys cover quotation, inspection, scheduler, service job card, dashboard, AMC quote/contract, VAS pricing/sales, rate card, D+I installation pricing, Thomson proposal, and revenue dashboard. The code verifies sessions and roles server-side; the browser role must never become the authorization source. The replacement will use Supabase Auth for identity and PostgreSQL-managed application roles/permissions.

Key operations include `loginUser`, `validateSession`, `logoutUser`, `changeMyPassword`, `adminListUsers`, `adminAddUser`, `adminResetPassword`, `adminDeleteUser`, `adminGetRolePermissions`, `adminSaveRolePermissions`, `logActivity`, and `adminListActivity`. The legacy password/session implementation is reference-only and must not be copied into the replacement. Do not copy the source's seeded credentials into documentation or a repository.

### Files, workbooks, pricing, dashboards, and reports

Drive-backed files include:

- Master service budget workbook used for VAS/AMC/Thomson/rate-card parsing.
- Revenue dashboard workbook.
- Stock valuation workbook.
- Job-card attachment files.

The relevant functions are `adminUploadMasterExcel`, `getMasterExcelInfo`, `getMasterExcelData`, `adminUploadDashboardExcel`, `getDashboardExcelInfo`, `getDashboardExcelData`, `adminUploadStockExcel`, `getStockExcelInfo`, `getStockExcelData`, and `uploadJobCardAttachments`. Files are replaced by administrators and served as base64 to the browser in the legacy application. The replacement must use private object storage, signed URLs, MIME/size validation, audit records, and no public-by-link sharing.

Admin-editable configuration includes:

- VAS price bands and profit split: `VAS_PriceBands_Admin`, `VAS_ProfitSplit_Admin`.
- VAS pricing parameters: `VAS_PricingParams_Admin`.
- Service rate card: `ServiceRateCard_Admin`.
- AMC pricing: `AMC_Pricing_Admin`.
- D+I pricing: `DandI_Pricing_Admin`.

The corresponding get/save/reset functions are present in the source around the VAS, rate-card, AMC, and D+I sections. These configurations need versioning, validation, effective dates, and audit history before production cutover.

Dashboard functions include `refreshDashboardCacheInBackground`, `installDashboardBackgroundRefreshTrigger`, `getDashboardOverview`, `getReportRows`, `getDashboardSnapshot`, and `invalidateDashboardCache`. The legacy cache is short-lived and rebuilds from multiple sheets. The replacement should use database queries/materialized summaries or a bounded cache with explicit invalidation and freshness metadata.

Phone repair admin functions (`adminPreviewPhoneRepairs`, `adminApplyPhoneRepairs`) infer missing UAE mobile prefixes and may rewrite historical values. This is migration/admin tooling, not Phase 2 MVP; any replacement must require preview, authorization, audit, and explicit confirmation.

- Login, password change, session restore, logout, theme preference, role-based tab visibility, and management read-only mode.
- Dashboard overview, cached snapshot loading, record counts, scheduler counts, reports, and activity/changelog views.

- Scheduler: new request, complaint inbox, assignment board, all appointments, monthly calendar, technician management, B2B branch selection, duplicate/draft scheduling, status changes, job links, WhatsApp helpers, and ICS links.

It performs client checks but calls `submitCustomerComplaint`; server-side validation is authoritative.

## Migration priorities

### Phase 2 MVP

1. Supabase Auth session integration and server-side RBAC.
2. Public complaint registration with rate limiting, validation, and `CMP-yymmdd-XXX` generation.
3. Complaint inbox, CCE notes/status updates, and customer-to-appointment linkage.
4. Technician master, appointment creation/editing/assignment, status transitions, and draft schedules.
5. Transactional appointment linkage and rollback behavior.
6. Dashboard counts/list filters and ICS generation.
7. Email remains disabled behind an explicit feature flag.

### Required before production cutover

1. Complete parity for job cards, final-status locking, attachments, print views, quotations, inspections, AMC, VAS, D+I, Thomson, rate cards, and pricing overrides.
2. Workbook import/export and private file storage with preview, validation, and audit trails.
3. Reports, XLSX exports, dashboards, activity logs, admin user/permission controls, and historical references.
4. Data importers, reconciliation, idempotency tests, representative-record verification, and attachment mapping.
5. Security controls: rate limits, secure headers, CSRF strategy for session cookies, private storage, signed URLs, least privilege, audit logging, dependency scanning, and secret scanning.
6. Business acceptance and rollback rehearsal while Apps Script remains available.

### Post-cutover candidates

- Enhanced notifications after approved templates and business email identity are available.
- Background refresh/cron optimization after core workflows are stable.
- Advanced operational analytics and new dashboard views.
- Replacement of historical phone-repair tooling with a governed data-quality workflow.
- Retirement of Apps Script only after the defined rollback period and written approval.
